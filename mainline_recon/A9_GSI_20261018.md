# 真 A9 arm32 system 到手（phhusson GSI v123）与本轮修掉的四个错（2026-10-18）

## 1. 结论先说

本机**第一次拿到了一份真实的 Android 9 / API 28 / armeabi-v7a 系统镜像**，并把它改造成
可直接刷进 Z1 `android`(p4) 分区的形态：

```

        资产 system-arm-aonly-vanilla-nosu.img.xz  339,017,396 B（xz，无 GApps、无 su）

完整性  xz -t 通过（整流 CRC64）→ 与代理无关，代理只搬字节；sha256(system.img.xz)=cde1bbf6581d04930c1c44d051666dcccfcf230cae7c07bb1e566be086adb5fa
展开    Android sparse v1.0 → raw ext4 1,313,583,104 B
```

## 2. 唯一剩下的缺口：A9 自己的 PID1（两个二进制）

A-only 的 GSI **刻意不含** `/system/bin/init` 与 `/system/bin/ueventd`（它假定设备的 boot ramdisk
提供 first-stage）。全镜像遍历确认：`find` 只找到 `/etc/init/*.rc` 这类脚本，没有任何 `init` ELF。
所以这份 system 现在刷上去，交棒链会停在：

```
[a9hand] RESULT_STEP_handoff=FAIL(没找到可执行的 A9 init：查过 /system/bin/init、…、/sbin/a9_init)
```
这不是 system 内容的问题，而是**差两个文件**。本机已把它做成普通输入件：

```
android9/mainline/rootdir/bin/init          # EM_ARM 的 A9 init
android9/mainline/rootdir/bin/ueventd       # 同上
```
放进去后重跑 `z1_a9_mainline_system.py`，两个二进制就随 device 层一起进 `<P>/bin`，
`z1_a9_system_accept.py` 与 `z1_a9_flashpkg.sh` 的闸会放行，包即为最终安卓成品。
兜底通道也已就位：交棒脚本在 `/system/bin/init` 不存在但 ramdisk 里有 `/sbin/a9_init` 时，
临时把 `/system` 转 rw 种入 init/ueventd、sync、立即回 ro，并打 `RESULT_STEP_seed=OK|FAIL`。
来源任选：任意一份 arm32 Android 9（LOS 16.0 / AOSP 9 `aosp_arm`）的 system.img 里取即可。
取料通道见 `A9_SYSTEM_ADAPT_20261018.md` §10（分片 sha 逐片校验）。
投件后先自证再重跑（脚本判三件事：EM_ARM、含 `second_stage` 参数串、PT_INTERP 不能是 linker64）：

```sh
bash tools/z1/z1_a9_check_seed.sh          # SEED_FAIL=0 才算件对了
python3 tools/z1/z1_a9_mainline_system.py --system out/gsi_v123/system.raw.img --out out/a9sys_gsi
tools/z1/z1_a9_flashpkg.sh --boot out/boot_mainline_a9p9_D1_1b.img --system out/a9sys_gsi/system_mainline.img
```

## 3. 本轮被真镜像抓出来的四个错（都是"只在夹具上测过"的分支）

1. **仓里的 sparse 解析是错的，且对任何真 sparse 镜像都不成立。** 原实现把 magic 写成
   `0x3AFF26AF`、头部按 9 个 `u32` 解（真实是 `0xED26FF3A` + `u32 magic,u16 major,u16 minor,
   u16 file_hdr_sz,u16 chunk_hdr_sz,u32 blk_sz,u32 total_blks,u32 total_chunks,u32 crc` = 28 B）。
   新模块 `tools/z1/z1_a9_sparse2raw.py` 按真布局实现，并逐 chunk 校验 `total_sz` 算术与块数合计。
2. **`DONT_CARE` 不推进输出偏移** → 第一个空洞之后的所有 RAW 全写到错位置，根 inode 被写坏；
   我随后 `e2fsck -fy` 一把，把 `/system` 直接清成空壳（只剩 916 MB 的 lost+found）。
   这解释了"为什么必须先 `e2fsck -fn` 看报告、再看 `debugfs ls`，不能信 rc"。修好后
   `dumpe2fs` 认块、`e2fsck -fn` rc=0、`debugfs` 能列 2859 条路径。
3. **`image_write` 假设了 `/system/etc` 这种多级目录已存在。** 真 GSI 的 `/vendor` 是
   **符号链接**（`stat` 显示 Type: symlink, Size 7），debugfs `cd` 进不去、`write` 静默落别处、
   读回 0 B。现在 `dir_kind()` 先分辨 dir/link/missing，落点只认真目录；
   设备级 manifest 也改投 `/etc/z1_device_manifest.xml` 中转（绝不覆盖 AOSP 的
   `/etc/vintf/manifest.xml`），由交棒脚本在运行时放进可写的 `/vendor/manifest.xml`
   （`RESULT_STEP_manifest=PLACED`）。
4. **A9 `hwservicemanager.rc` 里本来就有 `disabled`。** 真 GSI 原生就是这样
   （`class animation` + `onrestart class_restart hal/early_hal`），不是 stock 线那套代偿。
   所以这条判据的**归因**要改准：它表示"服务待启用"，不表示"stock 残留没撤"；
   处置动作不变（adapter 去掉 `disabled`，改造后镜像里就没有了），
   验收器仍会在未改造的镜像上报它 —— 因为最终镜像里 hwservicemanager 必须能起来。

## 4. 这份包现在能拿到什么板上真值（以及不能声称什么）

能拿到：`[a9hand]` 的分区识别（按 scatter 字节数认 android）、`by-name/*` 建立、只读挂载真 A9 ext4、
`RESULT_STEP_vendor`（tmpfs/bind/UNMOUNTED 三态）、`RESULT_STEP_fstab`（PLACED/MISS/OK/FAIL）、
`RESULT_STEP_selinux`（A9 GSI 只有 `plat_sepolicy.cil`，无 precompiled → 期望 NOPOLICY）、
以及 `[a9dev]/[a9probe]/[a9cfg]` 三段既有证据。

**不能声称**：安卓界面起来了。§2 那两个二进制到位之前，这条链不可能进 second-stage，
所以本目标仍未达成，我不把它标记完成。

## 5. 复现命令

```sh
cd <工作区根>
# 取料（代理口 + 完整性自证）
curl -sSL -o out/gsi_v123/system.img.xz "https://gh-proxy.com/https://github.com/phhusson/treble_experimentations/releases/download/v123/system-arm-aonly-vanilla-nosu.img.xz"
xz -t out/gsi_v123/system.img.xz && xz -dk -c out/gsi_v123/system.img.xz > out/gsi_v123/system.img
python3 a9_wt/tools/z1/z1_a9_sparse2raw.py out/gsi_v123/system.img out/gsi_v123/system.raw.img
# 裁剪 + 收缩（内容层改动都在 ADAPT_REPORT/本文件里留痕，原始 xz 保留可回溯）
sudo mount -o loop,rw out/gsi_v123/system.raw.img /mnt && sudo rm -rf /mnt/{lib/vndk-26,lib/vndk-27,framework/oat} && sudo umount /mnt
e2fsck -fy out/gsi_v123/system.raw.img && resize2fs -f out/gsi_v123/system.raw.img 227000
# 改造 + 出片
python3 a9_wt/tools/z1/z1_a9_mainline_system.py --system out/gsi_v123/system.raw.img --out out/a9sys_gsi
```

## 6. 磁盘账（哪些是原件、哪些可重算，将来清理时别删错）

| 路径 | 大小 | 性质 |
|---|---|---|
| `out/gsi_v123/system.img.xz` | 339,017,396 B | **原件**，sha256 `cde1bbf6…`，`xz -t` 已验；唯一不可再生 |
| `out/gsi_v123/system.img` | 973,586,676 B | 可重算（`xz -dk`） |
| `out/gsi_v123/system.raw.img` | 929,792,000 B | 可重算（sparse2raw + 裁剪 + resize2fs，命令见 §5） |
| `out/system_a9_gsi_v123_raw.img` | 929,792,000 B | 同上的一份留档副本，可重算 |
| `out/a9sys_gsi/system_mainline.img` | 929,792,000 B | 可重算（adapter，ADAPT_REPORT.json 留痕） |
| `out/A9_flashpkg_p10_gsi_preinit/` | 935,448,576 B | 可重算（上面两件 + scatter） |

也就是说：真需要长期保存的只有那个 339 MB 的 xz 原件（以及仓里的脚本与台账）。

## 7. A9 的 PID1 找到了：就在自家 z1-android9 的 release 里（只花 6 MB）

`lxjuyn/z1-android9`（**私有仓**，匿名访问 404）有 14 个 Z1 Android 9 的 release。取其中
`Linux7-20261006-r2` 的 **`boot.img`（6,166,528 B，sha256 与 release 的 SHA256SUMS 逐字一致）**，
解出它的 ramdisk（gzip+newc cpio，56 条目），里面有：

```
init            ELF 32-bit ARM, statically linked, 1,637,512 B, 含 second_stage 参数串
sbin/ueventd    -> symlink to ../init      （A9 的设计：一个二进制按 argv[0] 分角色）
init.rc / init.environ.rc / init.z1.rc / init.z1.network.rc / init.zygote32.rc
ueventd.rc / ueventd.z1.rc / fstab.z1 / default.prop
sepolicy(384,652 B) + plat_file_contexts + plat_{hwservice,property,seapp,service}_contexts
```
`init.zygote32.rc` 直接印证这份 A9 是 **arm32 zygote**，与本树的 `ARCH=arm` 对得上。
`fstab.z1` 与我们仓里那份 **逐字相同（diff 0 行）** —— 两条线在分区表这块是对得上的；
`init.z1.rc`(66 行差异)/`ueventd.z1.rc`(50 行)/`init.z1.network.rc`(51 行) 不同，是因为我们的
那份按 P3/P7/P8 的**内建**符号重写（他们那份仍按 stock 的 41 条 insmod 写）。

投件与出片（本机实跑）：
```
android9/mainline/rootdir/bin/{init,ueventd}   # 从他们 ramdisk 取出的同一 ELF（ueventd 用副本）
z1_a9_check_seed.sh -> SEED_FAIL=0
z1_a9_mainline_system.py -> 落点 8 处读回一致，含 /bin/init、/bin/ueventd
z1_a9_system_accept.py --expect-adapted -> CHECKS=17 FAIL=0 WARN=2  SYS_ACCEPT=ACCEPT
z1_a9_flashpkg.sh --boot out/boot_mainline_a9p9_D1_1b.img --system out/a9sys_p11/system_mainline.img
  -> rc=0，包 out/A9_flashpkg_p11_android（bootimg+android 两行放行，其余 9 个分区不下载）
  boot.img  d7b428c1…   system.img ecbee094…（929,792,000 B，p4 余 13,926,400 B）
回归：SPARSE 5/5、SYS_ACCEPT 4/4、HANDOFF 8/8 全绿。
```

两个刻意的保留，别当成已解决：
1. **没把他们那份 `sepolicy` 混投进 GSI**。GSI 自带的是它自己那套 cil，与 LOS16 编译出的策略
   不同源；混投会在标签上制造更难查的问题。现在交棒会打 `RESULT_STEP_selinux=NOPOLICY`，
   首启靠 dts 的 `androidboot.selinux=permissive`。要投就配他们那套 system（见下）。
2. **那份 `system.raw.img`（943,718,400 B，正好等于 p4）没下成**：我第一次的分段下载器有 bug
   （段存在就跳过 dd），写出来只有 124,780,544 B、sha 不符 `b6daba24…` —— 是 sha 校验把它抓出来的。
   那份才是与这套 init/sepolicy 同源的权威 system；重下被你叫停，所以现在的包用 GSI 那套。

入库纪律：从私有仓取出的 `init`/`ueventd`/`sepolicy` **只做本地输入件，不提交到公开仓**
（`android9/mainline/rootdir/.gitignore` 与 `sepolicy/.gitignore` 已挡住），仓里只留 sha256 与来源：
`init`=`285382ea87dada34629516af590626e4932ebe47b2626197b5da8bd8273b083e`(1,637,512 B)、
`sepolicy`=`e01a4c589f1363bbaf0b6149be60fe81a6dd30af101f8215eb34b8eca4674f9c`(384,652 B)。
重取命令：`curl -sSL -H "Accept: application/octet-stream" https://api.github.com/repos/lxjuyn/z1-android9/releases/assets/613267971 -o boot.img`
→ `z1_a9_flashpkg` 之外用 `unpack_bootimg`/本仓的 gzip+cpio 兜底扫描解 ramdisk。

**这两个包都还没上板**，所以我不把目标标记完成：差一次串口实测来判定 SELinux、/vendor、
HIDL 三条未知。
