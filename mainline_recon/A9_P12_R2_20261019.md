## 一、本轮抓出的洞：`debugfs write` 撞已存在路径静默失败 + 装包链丢退出码

第一次跑 r2 路线时 adapter 报
`ABORT: 模块 /lib/modules/z1-network/xt_IDLETIMER.ko 读回 sha 不一致（期望 8b28e429 实得 1887b5dd）`
（rc=3），**但包照样出好了、还拿到 `SYS_ACCEPT=ACCEPT`**。两处各有其因：

1. **r2 的 system 本来就自带这两个 .ko**（`xt_quota2` sha `c6ac4c1a…`、`xt_IDLETIMER` `1887b5dd…`）。
   adapter 的模块落点没做"已存在先 rm"，而 `debugfs write` 撞已存在条目是**静默失败、退出码仍为 0**，
   于是读回拿到的是旧件。（同文件的 device 层那支早就有 `rm` 再 `write`，模块这支漏了。）
2. **`z1_a9_use_r2_system.sh` 把 adapter 直接管进 `tail`**，`set -o pipefail` 也救不了——它没接 rc，
   半改造镜像继续进 flashpkg。这是 P3"mkbootimg 静默丢 ramdisk 而校验器仍报 VALID"那一类错的**第二次显形**：
   管道末端命令的退出码不代表链路成功。现改为落日志 + `rc=$?` + 非零即 `exit 3`，
   并在装包后再 `grep -q 'SYS_ACCEPT=ACCEPT'`。

**覆盖的取舍依据（如实记）**：r2 原装那两个 .ko 的 vermagic **也是 `7.0.0-rc7-z1+`**（同版本串，
尺寸各差 8 B），所以覆盖的理由**不是**"vermagic 对不上"，而是"与本轮实际出货的 zImage 同树同产物"
这条更强、可核。`.ko` 与 rc/fstab 归同一侧（坚持覆盖），不像 `init`/`ueventd` 那种 ELF 副本可以让位。

## 二、闸因此加严：`net_modules` 现在比 sha，不只验 magic

只验 ELF magic + `e_machine` 会放过"载荷自带的另一份 .ko"——它 magic 全对、e_machine 全对，
但不是我这一棵树的产物。现在 `z1_a9_system_accept.py` 把 `android9/mainline/network/modules.json`
的 sha 拿来逐文件比，不符即 FAIL。
**负测试**：拿那次半改造出来的镜像喂加强后的闸 → `FAIL net_modules` 点名两个文件与两组 sha，
`SYS_ACCEPT=REJECT`。该坏件留证为 `out/A9_flashpkg_p12_r2.BAD_halfadapt/`（勿刷，已作废）。

## 三、r2 实测答复了几条原先"只能上板才知道"的问题

- **PID1**：r2 的 system **没有** `/bin/init`、也没有 `ueventd`（LOS16 把它们放 boot ramdisk），
  所以"r2 权威 system 自带 init/ueventd"那句是错的（多半当时看的是碎片赝品或 r2 的 boot.img）。
  我们的两个投件正是补这个缺，且 provenance 同源：`rootdir/bin/{init,ueventd}` 取自 r2 那条 release，
  1,637,512 B、EM_ARM、静态、`check_seed` SEED_FAIL=0。二者**字节相同是正确的**——A9 里 `ueventd`
  就是 `init` 的符号链接，`init` 在 `main()` 按 argv[0] 分派到 `ueventd_main`；投成两个副本等价。
  投件内 `ueventd` 串 7 处、`second_stage` 1 处、`early-init` 1 处、**`selinux_setup` 0 处** ——
  后者正是交棒脚本"reexec 直接到 second_stage"那条血统分支的判据，已被 `HANDOFF_SELFTEST` CASE7 覆盖。
- **SELinux**：r2 与 GSI **两份载荷都没有任何策略镜像**（`precompiled_sepolicy`/`plat_sepolicy.cil` 零命中），
  所以首轮必然是 `RESULT_STEP_selinux=NOPOLICY`，靠 dts bootargs 的 `androidboot.selinux=permissive` 过。
  这把这条未知从"会不会炸"降级成"首轮按 permissive 走，收紧要另找策略源"。
  注意 `a9_wt/android9/mainline/sepolicy/z1_a9_precompiled_sepolicy.from_los16` 那份**是 file_contexts
  不是策略镜像**（magic `0xF97CFF8C` ver 8），`policy_is_loadable` 会拒绝投它 —— 别手塞。
- **cgroup**：原先怀疑 A9 init 要 `blkio`/`pids`（本内核 `CONFIG_BLK_CGROUP`、`CONFIG_CGROUP_PIDS` 均 ABSENT）。
  **已定案为"不需要改内核"**，证据三条：① r2 与 GSI 两份载荷都没有 `cgroups.json`/`task_profiles.json`
  （r2 枚举 2508 条、GSI 2872 条，均零命中）；② 要出货的那枚 `init` 二进制里**没有任何** `cgroups.json`
  /`task_profiles.json` 路径串（`strings` 只剩 legacy 的 "process cgroup" 那几串），所以缺那两个文件
  不构成 PID1 的 FATAL 风险；③ 直接取载荷 61 个 rc 里真正的 `mount cgroup` 行，唯一要求的控制器是
  **`bfqio`**（来自 `/etc/init/lineage-iosched.rc`，LineageOS iOSched 的专有内核补丁，mainline 无此物），
  另有 `/dev/cpuctl/cpu.notify_on_migrate` 这类 stock/MTK 专有节点。两处都会在板上记 error 但**非致命**。
  据此**不开** `CGROUP_BLKCG`/`CGROUP_PIDS`：为一个已被证据排除的猜测去重编 zImage、动已验证的启动链，
  是本项目的纪律明令禁止的。上板只需在日志里确认这两条 error 不升级成 bootloop。
