# 超预算时 boot.img 会静默丢掉整个 ramdisk（2026-10-18 实测复现并封堵）

## 怎么发现的

为了证明"A9 ramdisk 一到就能出片"，我用两颗合成的 A9 形状 ramdisk 做了正/负测试：
合规的一颗（body 204,890）与**故意超预算**的一颗（body 2,205,312，投影超出 550,868 B）。
负测试的预期结果是"被拒"，实际结果是：

```
余量 = -550,868   RESULT: VALID      文件 4,636,672 B
```

也就是说 —— **它出片了，而且校验器说 VALID**。查镜像内部：

```
ramdisk: 0x46c000+0
NOTE: ROOTFS payload is neither gzip nor newc cpio; initrd checks skipped
```

`mkbootimg` 在装不下时**不是报错，而是把 ramdisk 整个丢掉**（`ramdisk_size=0`），
产出的镜像尺寸反而"合规"了。这种镜像刷进去的表现是内核没有 initramfs →
`VFS: Unable to mount root fs`，而串口现场长得像"内核回归/启动链坏了"，
会把人往错的方向带走一整轮刷机 —— 与 v13.1 的 initrd 截断是同一类事故（静默的尺寸不一致）。

同时这暴露了 `tools/validate_mtk_boot.py` 的一个盲区：ramdisk 缺失只记 `NOTE`（提示），
不进 `errors`，所以照样 `RESULT: VALID`。

## 已封堵（三层）

1. **打包前置预算闸门**（`tools/z1/z1_a9_p2.sh`）：先算 `zImage + dtb + ramdisk + 4096`
   与 6,291,456 比较，超出就 `exit 6` 拒绝打包，**不给 mkbootimg 静默丢弃的机会**。
2. **校验器加 `--require-ramdisk`**（只增开关，默认关闭，不影响既有调用）：
   `ramdisk_size=0`、MTK ROOTFS 区过小、载荷既非 gzip 又非 newc cpio —— 三种情况一律
   `errors` → `RESULT: INVALID`。用新开关复测：超预算镜像 INVALID，两张正式镜像仍 VALID。
   同一份加固版校验器随分支存档为 `tools/z1/validate_mtk_boot.py`（工作区根 `tools/` 不在本
   git 仓内，之前只有一份本地副本，台账里带它的 sha256 以便发现漂移）。
3. **载荷逐字节存在性核验**（打完之后）：在镜像里搜 `zImage` 与 ramdisk 的前 64 KB，
   命中后再比对整段字节，打印 `PAYLOAD-OK <名字>: 在 <偏移> 处逐字节完整(<长度> B)`。
   不靠手算偏移——MTK 的 KERNEL/ROOTFS 包装头容易算错，我这次就先算错过一次，
   差点把"格式不同"误判成"镜像坏了"。

## 实测得到的预算真值

| 项 | P4 值 |
|---|---|
| zImage | 4,612,608 B |
| dtb | 19,796(1b) / 19,808(4b) B |
| 探针 ramdisk（带 512B MTK 头） | 1,276,824 B（body 1,276,312） |
| 镜像尺寸 | 5,914,624 B，余量 **376,832 B** |
| **A9 generic ramdisk 上限** | **约 1,654,944 B**（≈1.58 MiB，含 512B 头） |

这条上限就是交接给 LOS16 构建机的硬指标：ramdisk 超过它，本机会**在打包前**拒绝，
而不是产出一张刷进去没有 initrd 的镜像。
