# A9 P12（2026-10-19）：交付件 inode 类型位被抹平的根因与封堵

> **本文件的 §五/§六 已被 `A9_P12_R2_20261019.md` 取代**（r2 那份真·Z1 system 已按 SHA256SUMS 逐字节
> 重取核对并完成出全片；"仍缺的输入"与"GitHub 出口断"两节均已失效）。本文件的 **§一~§四（i_mode 类型位
> 根因、模块投递、三道闸、defconfig 单一来源化）仍然有效**，是坑 10 的出处。

## 一句话

P10/P11 那两版"SYS_ACCEPT=ACCEPT"的包**不能当安卓成品刷**：adapter 用 debugfs 原地写文件时把
`i_mode` 的类型位覆盖没了，投递的 10 个文件全部 `Type: bad type`——权限位、内容、`debugfs cat`
读回都正常，唯独内核打不开这些文件。本轮修根因、加两道新闸，出 `out/A9_final_p12/pkg`。

## 一、根因（两个坑叠加）

`set_inode_field` 的值由 debugfs 按 `strtoul(base 0)` 解析：

1. `img_mode()` 原样喂 `'0644'/'0755'` → 八进制 420/493 → **整个 i_mode 被写成不含 S_IFREG 的值**。
   表现：`debugfs stat` 报 `Type: bad type`，`Mode:` 看着完全正确。
2. 补救那句喂 `'100755'` → 被按**十进制** 100755 解析，`> 65535` 直接被拒；而 debugfs 只把错误
   打到 stdout，**退出码仍是 0**，于是 `dbg()` 的 returncode 检查放它过关——"补可执行位"这一步
   静默空转了一整轮。

旁证被误读过：e2fsck 一直报 `Inode 1654/1655/1656… 的 i_blocks 为 N，应为 0`，`rc=4`，被
P10/P11 归类成"原厂打包器的记账瑕疵，可直接刷"。实际是 e2fsck 认不出这个 inode 的类型，
所以按"不该占块"来算——它正是类型位丢失的直接信号。现已把 `i_blocks` 加进 e2fsck 的结构性
损坏征兆正则，出现即 FAIL。

修正：`img_mode()` 统一输出 `0%o` 形式且强制带 `0o100000|perm`；`image_write()` 与可执行位补写
之后各调一次新增的 `assert_regular()`（解析 stat 文本，不看退出码）。

## 二、新增的三道闸（都做过正/负双向测试）

| 闸 | 判据 | 负测试 |
|---|---|---|
| `file_type`（system_accept，`--expect-adapted`） | 投递件 `i_mode` 类型位必须 `regular` | 旧 P11 镜像 → FAIL，点名 8 个坏 inode |
| `net_modules`（同上） | rc 里每条 `insmod` 的绝对路径必须在镜像内命中且是 EM_ARM ELF | 旧 P11 无 `/lib/modules` → FAIL 两条 |
| `ramdisk_accept` 的 stock 串扫描 | 命中只允许在 `sbin/`（那是撤销逻辑的文案），`/init` 或 rc 里出现照旧判死 | 往 `/init` 塞 `ro.z1.stock_kernel=1` → 仍 REJECT |

顺带纠正一条旧误判：`z1_a9_ramdisk_accept.py` 曾 REJECT `out/ramdisk_a9p9.gz`，理由是
`sbin/z1_a9_handoff.sh` 含 `/z1_stock_kernel` 串。实测全 ramdisk 只有这一个文件带该串，且两处
都在注释与 DIAG 文案里（写的是"本镜像已无该标记"）——它在说明撤销，不是残留门控。而同一脚本
L2 形态 B 又强制要求交棒件在位，两条规则互相矛盾。现按本文件里 `/dev/ion` 已有的 `sbin/` 豁免
先例处理，并保留 WARN 让操作者看得见。

## 三、netfilter 模块此前根本没交付

`init.z1.network.rc` 要 insmod `/system/lib/modules/z1-network/xt_{IDLETIMER,quota2}.ko`，
而 `z1_a9_mainline_system.py`、`z1_a9_flashpkg.sh` 里对 `.ko`/`modules`/`z1-network` **零引用**——
实测 P11 镜像连 `/lib/modules` 目录都不存在，交棒脚本也不负责装载。A9 netd 开机下发 quota/
IDLETIMER 规则会静默失败。

现在 adapter 按 `android9/mainline/network/modules.json` 驱动投递：从本树取 `.ko`、**sha256 与
清单强校验**（不符即 ABORT，绝不沿用 stock 3.4.67 时代的字节），落到 `<P>/lib/modules/z1-network/`，
写后读回比 sha。落点只此一个——不能往镜像根新建 `/system/`，因为 `z1_a9_handoff.sh:182` 见到
`$SYSROOT/system` 存在会做 `mount -o bind` 下移一层，凭空造那个目录会把整个根搞错位。

两个模块实测 14,808 + 10,572 = 25 KB，镜像余量 13.9 MB。

## 四、defconfig 单一来源化（HANDOFF §7 第 3 条）

审计结果：`z1_defconfig` 仍缺 **97 项**当前 `.config` 里 `=y/=m` 的 A9 相关符号（整条
`NETFILTER_XTABLES_LEGACY`/`IP_{NF,MANGLE,NAT,RAW}` legacy 链、`SECURITY_SELINUX_DEVELOP`、
`MEDIATEK_WATCHDOG`、`DM_BUFIO`、`EXT4_FS_POSIX_ACL`、IPv6 netfilter 全家…）。任何人跑一次
`make z1_defconfig`，拿到的就是一个 A9 起不来的内核。

处置：不动 bring-up 基线用的 `z1_defconfig`，改为从**已验证的 A9 `.config`** 反向生成
`arch/arm/configs/mt6572-z1_a9_defconfig`（513 行）。往返回归做实：移开基准 `.config` →
`make mt6572-z1_a9_defconfig` 重建 → 与基准 **6683 行逐字节零差异**，133 项 A9 相关符号全等
（含 `ANDROID_BINDER_DEVICES="binder,hwbinder,vndbinder"`、`ANDROID_ASHMEM=y`、
`SECURITY_SELINUX=y`、`IP_NF_IPTABLES_LEGACY=y`、`MEDIATEK_WATCHDOG=y`）。

A9 出片请用 `make mt6572-z1_a9_defconfig`，别用 `z1_defconfig`。

## 六、还缺的那一件：真正为 Z1 构建的 A9 system

`out/z1a9_r2/system.raw.img`（应等于 android 分区 943,718,400 B）**不可用**：
- 实测 sha `fa80c785a584…` ≠ release `SHA256SUMS.txt` 的 `b6daba2417de…`（同目录 `boot.img` 反而一致）；
- `e2fsck -fn` 报扩展属性块 190827–190830 损坏、`h_blocks > 1`，`debugfs cat /build.prop` 直接读空；
- 来历也对不上：`dl_sys.log` 记的是 `http=404`，目录里留着 `.g.0`(178 MB)/`.g.29`(3.3 MB) 碎片，
  而该件 mtime 15:12 晚于所有下载日志——这份是碎片拼出来的，尺寸刚好凑满分区所以没被尺寸闸拦下。
