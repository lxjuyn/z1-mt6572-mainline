# USB 串口 (ttyGS0) shell 卡 `>` 续行 / 换行不提交 — 联网调研 (2026-08-15)

> 只读联网调研 (tavily / firecrawl)。不改本地文件。与本地源码级分析 `mainline_recon/ACM_TERMIOS_DEEP_20260815.md` 交叉核对, 结论互相印证。
> 现场: `getty -L -n -l /bin/sh 115200 ttyGS0`, 命令回显但回车不执行, shell 停在 `> `; 设备屏幕 console (UART) 正常。

---

## 0. 结论一句话

**`> ` 是 busybox ash 的 PS2 续行提示符, 不是 getty 死锁。出现它 = shell 解析器认为当前输入行"未闭合"。回车(Enter)默认发的是 CR(0x0d), 而 ash 词法器里只有 LF(0x0a) 是命令终结符(CNL), CR(0x0d) 只是普通单词字符(CWORD)——一旦设备侧 tty 没把 CR→LF(ICRNL 不在位 / tty 处于 raw 窗口), 输入行就永远等不到终结符, 表现为"命令回显了但换行不提交、一直 `>`"。** busybox getty 本身在 exec sh 前会把 tty 正确设成 cooked(ICANON|ICRNL|ECHO|ONLCR), 内核 g_serial 默认 termios 也是 cooked; 真正的坑在 **getty 的 raw 初始化窗口 / 双 getty 竞争改 termios / 主机只发裸 CR 而 ICRNL 恰好被清** 三者叠加(本机双 getty 结构 bug 见 ACM_TERMIOS_DEEP 3.5)。

## 1. 换行不提交的常见根因 (归纳, 均带外部依据)

### 根因 A — CR/LF 翻译不匹配 (最常见, 单链路下主因)
- 标准终端协议: 键盘 Enter 发 **CR (0x0d)**, 电脑回显/补 LF。canonical (cooked) 模式下内核 tty 行规程用 `icrnl` 把 CR→LF, 用 `onlcr` 把输出 LF→CRLF。
- 若设备侧 tty 的 **ICRNL 不在位**(raw 模式 / 被 getty raw 窗口或竞争进程清掉 / `stty -icrnl`), 主机 Enter 的裸 `\r` 原样进 shell 词法器, 而 ash 只认 `\n` 终结命令 → 行不提交, 出 PS2 `> `。
- 依据:
  - https://superuser.com/questions/714078/wrong-newline-character-over-serial-port-cr-instead-of-lf ("canonical mode translates CR→LF via `icrnl`, outgoing LF→CRLF via `onlcr`")
  - https://askubuntu.com/questions/441744/pressing-enter-produces-m-instead-of-a-newline ("most likely a problem with the stty terminal line setting rather than a TERM problem. Add `stty icrnl`")
  - https://stackoverflow.com/questions/12709326/logging-rs232-on-linux-without-waiting-for-newline (canonical 与 raw 差别: 只有 canonical 才按行缓冲/换行终结)
  - stty(1) 手册: `sane same as cread -ignbrk brkint -inlcr -igncr icrnl icanon ... echo ...`, `nl same as -icrnl -onlcr` — https://man7.org/linux/man-pages/man1/stty.1.html

### 根因 B — ash 词法: CR 是普通单词字符, 只有 LF 是命令终结
- busybox ash `PS2="> "`(默认), PS2 只在解析器行未闭合时打(未闭合 `'`/`"`/`` ` ``/`$(`/`\` 续行)。
- 语法表: byte 0x0a = `CNL`(命令终结), byte 0x0d = `CWORD`(普通单词字符)。`ls\r` 会被当命令名 `ls\r` 处理, 永远等真正的 LF。
- 依据(本地 1.36.1 构建树, 与板载 busybox 一致):
  - `shell/ash.c:2143` `{ VSTRFIXED|VTEXTFIXED, "PS2=> ", NULL }`
  - `shell/ash.c:3012-3013` `#define CWORD 0 / #define CNL 1`; 语法表 `SIT_ITEM(CNL, CNL, CNL, CNL) /* 1, \n */`(0x0d 落 CWORD 桶)
  - 上游源: https://github.com/mirror/busybox/blob/master/shell/ash.c

### 根因 C — getty 的 raw 初始化窗口 / 多进程抢同一 tty
- busybox getty 的流程是 **先打 raw**(`init_tty_attrs`: `c_iflag=0; c_lflag=0;` 读用户名用)→ **exec login/shell 前再设 cooked**(`finalize_tty_attrs`: `+ICANON|ISIG|ECHO|...`, `+ICRNL` 当 `G.eol=='\r'`)。`-n` 跳过读用户名, `G.eol` 保持默认 `'\r'` → ICRNL 一定会加。**单 getty 链路 termios 正确。**
- 但若有**两个进程(两个 getty / getty+其他程序)同时开同一 tty**, 各自 raw→cooked 来回覆盖 termios, 且两个 shell 分抢输入字节 → 就是"命令一半被别的进程吃掉"、termios 抖到 raw → `>`。TLDP 串口排障手册直接列出此现象并建议 `ps -alx` 检查同 tty 上的其他进程:
  - https://tldp.org/HOWTO/Text-Terminal-HOWTO-19.html ("two different processes opening the serial port... one process (perhaps the shell) reads what you type and at other times the other process reads what you type... use `ps -alx` to see what else is running on your ttySx and kill")
  - busybox getty.c 源码(init raw / finalize cooked / `-n` 行为): https://github.com/mirror/busybox/blob/master/loginutils/getty.c

### 根因 D — ash 行编辑器退化到 fgets 路径 (本机叠加项)
- 板上 busybox `FEATURE_EDITING=y`。交互 shell 正常走行编辑器(`libbb/lineedit.c`), **Enter 同时认 `\n` 和 `\r`**(lineedit.c:2588-2589), 提交时补 `\n` → 单链路下 CR/LF/CRLF 全能提交。
- 但 `read_line_input` 开头有一个退化分支: **ICANON 置位且 ECHO 被清** 时不打 raw、改用 `fgets()` 在 canonical 模式下等 `\n`。若此刻 ICRNL 也被清, 主机裸 CR 永远凑不齐 LF → fgets 永久阻塞, 命令回显但行不提交。
- ECHO 何时被清: getty `init_tty_attrs` 的 raw 窗口(`c_lflag=0`)+ 竞争 getty 时序交错。
- 依据: 本地 `libbb/lineedit.c:2478-2495`(fgets 退化条件)/ `2588-2595`(Enter 认 `\n` `\r`) / `2999-3002`(提交补 `\n`); 上游 https://github.com/mirror/busybox/blob/master/libbb/lineedit.c

### 排除项 (web+本地双重确认, 别再往这些方向找)
- **不是 "getty 没设 ICANON/ICRNL"**: getty `finalize_tty_attrs` 显式设 `ICANON|ISIG|ECHO|ECHOE|ECHOK|ECHOKE|ECHOCTL` + `ICRNL`(因 `G.eol=='\r'`)。`-n` 不影响该步。
- **不是 "g_serial 内核默认 raw"**: `u_serial.c` `driver->init_termios = tty_std_termios`(cooked: `c_iflag=ICRNL|IXON`, `c_lflag=ISIG|ICANON|ECHO|...`), 仅覆盖 c_cflag。即便不走 getty 直接 exec sh, 默认也是 cooked。
- **不是 "g_serial 没有行规程处理"**: `TTY_DRIVER_REAL_RAW` 只是 raw 模式下的快路径优化承诺(`n_tty.c` 算 `real_raw` 用), **不影响 cooked 模式的 ICANON/ICRNL 处理**。g_serial 无 `set_termios` 回调 = termios 完全由 N_TTY 行规程管, 驱动不干预。
- **不是 "主机 CDC 控制请求改 termios"**: `f_acm.c` `acm_complete_set_line_coding` 把主机 SET_LINE_CODING 只 `port_line_coding = *value` **记下来不应用**(源码注释 "REVISIT: we currently just remember this data"); SET_CONTROL_LINE_STATE 只存 handshake bits。主机侧拨号/波特率设置不会动 ttyGS0 的 iflag/lflag。
- 依据:
  - https://github.com/torvalds/linux/blob/master/drivers/usb/gadget/function/u_serial.c (init_termios=1562-1571, gs_tty_ops=911-922, TTY_DRIVER_REAL_RAW=1551)
  - https://github.com/torvalds/linux/blob/master/drivers/tty/tty_io.c (`tty_std_termios`=124-135)
  - https://github.com/torvalds/linux/blob/master/drivers/tty/n_tty.c (real_raw 计算, 约 1830-1848)
  - https://github.com/torvalds/linux/blob/master/drivers/usb/gadget/function/f_acm.c (line coding 只记录)
  - TTY_DRIVER_REAL_RAW 语义: https://docs.kernel.org/driver-api/tty/tty_driver.html

## 2. busybox getty 在 USB 串口 (非 UART tty) 的正确用法

**厂商/内核文档推荐形态 (单 getty + setsid):**
```sh
setsid getty -L -l /bin/sh -n 115200 /dev/ttyGS0
```
- https://docs.digi.com/resources/documentation/digidocs/90002286/reference/bsp/r_usb_device.htm ("baudrate is mandatory but irrelevant"; "setsid avoids permission problems when running getty from an interactive shell")
- https://www.kernel.org/doc/Documentation/usb/gadget_serial.txt / https://docs.kernel.org/usb/gadget_serial.html ("set up an /etc/inittab entry to run getty on it; /dev/ttyGS0 line should work like most any other serial port")

参数逐条 (busybox getty.c usage 段):
| 参数 | 含义 | 本场景 |
|---|---|---|
| `-L` | 设 CLOCAL(忽略载波检测) | **必须**。ACM 无真实 CD, 不加则主机断开时误判 DCD 掉线 SIGHUP 杀 shell。TLDP HOWTO 同款结论: "getty will be killed unless the local option has been used" |
| `-n` | 不提示读登录名 | 配 `-l /bin/sh` 时**必须**, 否则 getty 会卡在读用户名循环 |
| `-l LOGIN` | 用 LOGIN 代替 /bin/login | `-l /bin/sh` 直接起 shell |
| `-i` | 不显示 /etc/issue | **与 termios/回车无关, 不需要**。只是别让 issue 文本刷屏, 可选 |
| BAUD | 位置参数, gadget 串口上无意义 | 必须给个数字(位置占位), 写 115200 即可 |
| `-w`/`-m`/`-t`/`-I`/`-f`/`-H` | 调制解调器相关 | 全不需要 |
- busybox getty 手册页: https://busybox.net/downloads/BusyBox.html (getty 段); 源码: https://github.com/mirror/busybox/blob/master/loginutils/getty.c

**配套坑 (来自同场景社区的实测):**
- getty 打开 ttyGS0 在**主机未连接时可能 hang**(getty 的 open 阻塞), 社区用"等 /dev/ttyGS0 节点出现再起 getty"的循环规避——但**等待循环里的 getty 必须 setsid**, 否则 getty `setsid()` 失败即死(本机 ACM_TERMIOS_DEEP 3.5 后果 A)。
  - https://github.com/raspberrypi/linux/issues/1929 (ttyGS0 no-host hangs) / https://forums.raspberrypi.com/viewtopic.php?t=178917
- systemd 侧的等价物: `<EMAIL>`(等待/重启参数), 与本场景无关但可参考: https://forums.raspberrypi.com/viewtopic.php?t=312174, https://manski.net/articles/raspberry-pi/serial-console-on-zero2w

## 3. 修复建议 (按优先级)

### 3.1 根因级: 保证 ttyGS0 上只有一个 getty, 且等待循环版必须 setsid
(本机 ACM_TERMIOS_DEEP 5.1 已给完整改法; web 侧 TLDP HOWTO 亦点名"同 tty 多进程抢读"是这类症状的经典来源。)
```sh
# 删掉旧直接 getty 行; 等待循环改成:
(
  i=0
  while [ $i -lt 600 ]; do
    if [ -e /dev/ttyGS0 ]; then
      exec setsid $BB getty -L -n -l /bin/sh 115200 ttyGS0 vt100
    fi
    $BB mdev -s 2>/dev/null; $BB sleep 1; i=$((i+1))
  done
) </dev/null >/dev/null 2>&1 &
```

### 3.2 getty 前显式 stty 兜底 (把 ICRNL/ECHO/ICANON 钉死, 消除 fgets 退化与 raw 窗口漂移)
```sh
$BB stty -F /dev/ttyGS0 115200 icanon icrnl onlcr echo isig ixon opost 2>/dev/null
```
- `icrnl`=CR→LF 保回车提交; `icanon`=行缓冲; `echo`=回显(同时保证 ash 行编辑器走正常路径, 不进 fgets 退化分支); `onlcr opost`=输出换行正确。
- getty `finalize_tty_attrs` 会再设一遍同值, 幂等无害。
- 参考: askubuntu(stty icrnl), superuser(icrnl/onlcr), stty(1) 手册 `sane` 组合等价于此。

### 3.3 最简备选: 不用 getty, 直接 exec 交互 sh
busybox ash 交互行编辑器自带 CR/LF/CRLF 提交, 不需要 getty 的 termios 仪式:
```sh
exec setsid /bin/sh -i </dev/ttyGS0 >/dev/ttyGS0 2>&1
```
注意: 少 getty 的 TIOCSCTTY/前台 pgrp, 无 job control(可接受); 行编辑器仍靠 isatty 激活。

### 3.4 主机侧配合
- 终端/socat 用 **CRLF 或 LF** 提交, 别只发裸 CR:
  `socat - /dev/ttyACM0,raw,echo=0`
- 若坚持 CR 提交, 必须保证设备侧 ICRNL 在位(3.1/3.2 已兜)。
- 参考: https://superuser.com/questions/714078 (CR vs LF 收发), https://stackoverflow.com/questions/7812142 (screen 的 CR/LF)

### 3.5 getty 参数层面
- `-L` 保留(无载波)。`-n` 保留(跳过用户名)。`-i` 不需要(与 termios 无关)。

## 4. 上板验证清单 (30 秒)
1. `ps | grep -E 'getty|sh'` → ttyGS0 上**只有一个** getty。
2. shell 里 `stty -a < /dev/ttyGS0` → 确认 `icanon icrnl echo onlcr` 在位。
3. `echo $-` → 含 `i`(交互, 行编辑器激活)。
4. 分别用 CR / LF / CRLF 敲命令, 都应提交。
5. 若仍 `>`, 敲 `'` 或 `"` 或 `` ` `` 观察是否从"正常执行"变成"续行"——验证 PS2 机制。

## 6. 与本机分析的对照

- 本机 `mainline_recon/ACM_TERMIOS_DEEP_20260815.md`(源码级+qemu-arm 实测) 判定的**根因 = ttyGS0 双 getty 竞争 + ash 行编辑器 fgets 退化 + CR 当 CWORD**, 与本文根因 C/D/B 一一对应; web 侧 TLDP HOWTO、stty(1)、superuser/askubuntu 均给出同机制的外部佐证。
- 本机实测表(ACM_TERMIOS_DEEP §4): 单 getty 喂 `ls\n`/`ls\r`/`ls\r\n` 全部正常执行; 喂 `'`/`"`/`` ` ``/`$(` 出现持续 `>`; 双 getty 竞争输入分抢 — 与本文"PS2=未闭合构造"、"CR 不终结行"、"多进程抢 tty"三条机制完全吻合。
